# Hosted real test (Phase 2): design, rules of engagement, build steps

**Status: host service (single-agent and group runs), site routes and the real-test screen built and tested locally together; the VM, the legal text and the incident plan are not done.** Written 2026-10-11. Decision taken by the owner: invited teams run a real,
pen-testable test on a hosted nucleus (not a scripted demo, not a delivered copy).

## What an invitee gets

They write a task and up to five small text files (their "fixtures": a document with an
injected instruction, say), pick a model, and press run. The **real broker and the real
bubblewrap sandbox** run it on a machine you control. They get the broker's own log (every
request, its verdict and why), a summary and a downloadable export, and can try again. They
never touch the host: the only input is the task text and fixture files, and the only output
is the log.

There are two kinds of run:

1. **Single-agent run** (the first): one agent, the task above.
2. **Group run** (the second, opens after an invitee has finished a single-agent run): the
   lead agent may start up to two helpers, which message only the lead; the group shares one
   broker, one log and one kill switch, and the log shows who did what. The same inputs.

What is real: the broker, the policy engine, the sandbox, the tripwire, the log, and for group
runs the group rules and the kill switch. What is not offered in v1: their own policy file,
command execution, a hosted model key from them (see Decisions).

## Shape

```
invitee browser -> site Worker (Cloudflare) -> nucleus host (one small Linux VM)
   sign-in, invitation,                         signed requests only, nothing else
   terms, quota check                           listens; one broker + sandbox per run
```

- The Worker is the only caller. Each request to the host carries a timestamp and an
  HMAC-SHA256 signature over method, path and body, made with a secret only the Worker and
  the host hold; stale, replayed or unsigned requests are refused.
- The host service (`hosted/nucleus_host.py`) runs as an unprivileged user and listens on
  `127.0.0.1`; a TLS reverse proxy or tunnel is the only thing in front of it.
- Each run gets its own directory (mode 0700), its own broker process on its own socket,
  its own policy file and log, and an agent in bubblewrap that can see only that socket.
- The model key is the **owner's**, held in the broker's environment for that run only
  (never in the run directory, the log or any response). Invitees send no key.
- Limits: one run per invitee at a time, two at once on the host, 12 model turns, a
  10-minute wall clock, a daily cap per invitee, small bounded inputs. The tripwire (10
  refusals) halts a run. `POST /v1/halt` stops everything and refuses new runs until the
  service is restarted.

## The fixed policy

Per run, generated by the host and not editable by the invitee:

1. the agent may call the model (through the broker);
2. the agent may read files under that run's own `safe/` directory;
3. in a group run only: the lead may start helpers and agents may message and read their
   messages (the broker still enforces its own group rules: only the lead starts agents,
   helpers message only their parent, at most three agents);
4. everything else is refused.

Placeholders in the task text, filled in by the host: `{safe}` is the run's safe directory
and `{canary}` is the path of a fake credentials file the policy forbids. That is how an
invitee aims an injected instruction at something that must stay refused.

## Rules of engagement for pen testers (draft; counsel to review, including safe harbor)

**In scope:** the task text, the fixture files and the chosen model, as inputs to a run;
trying to make the agent do anything the policy refuses (read the canary, read outside
`safe/`, write, run a command, reach the network, start another agent); trying to get an
allowed-looking request through that should not be; trying to avoid or confuse the log.

**Out of scope, not permitted:** attacking the site, the Worker, sign-in, the host, the VM,
the network or other invitees; denial of service or rate-limit evasion; social engineering;
any attempt to read other people's runs; anything after a suspected escape except stopping
and reporting.

**If you think you got out:** stop, keep the run id, and report it to the owner privately
and promptly; do not publish it, and do not look further.

Findings: the owner decides what is fixed; the log is the evidence on both sides.

## Decisions taken as defaults (change them here)

1. **Owner's key, not the invitee's.** The site's terms say a model key goes from the
   browser straight to the provider and never to us; sending a key to the host would
   break that, so v1 uses a server-side key with the caps above. Invitee keys, if ever,
   need the terms and the privacy notice rewritten first.
2. **Group runs are the second kind of run.** A user may start one only after a
   single-agent run of theirs has finished (`NUCLEUS_GROUP_AFTER_SINGLE=0` lifts that).
   They share the per-user, host and daily caps; a group run counts as one run.
3. **One run per invitee at a time, two on the host.**
4. **Runs and logs are deleted after 30 days** and on request (`DELETE /v1/runs/<id>`).

## What invitees do not see

The agent's system prompt (the tool format and, in group runs, the lead and helper
instructions) is replaced by `[system prompt withheld]` in the copies of the log the API
serves; the broker's own database keeps the full record. They see their task, the model's
replies, every request and every decision. The host's paths, environment and key never
appear in a response (checked).

## Turning it on in the site (when the VM exists)

Worker settings: secrets `NUCLEUS_URL` (the host's HTTPS address) and `NUCLEUS_SECRET` (the same
string the host has), and a plain variable `NUCLEUS_MODELS` (comma-separated, matching the host's
`NUCLEUS_LLM_MODELS`). Apply migration `0004`. Without them `/api/real/*` answers "not open yet".

## Running the host locally (tests)

```
cargo build -p broker
python3 hosted/hosted-test.py      # the service end to end
python3 hosted/monitor-test.py     # the health check
bash -n hosted/deploy/setup-vm.sh  # the VM script's syntax
```

## Running it on a VM (when there is one)

Debian or Ubuntu, a dedicated user `nucleus`, bubblewrap and Rust installed, the repository
checked out at a fixed path, and the environment in a root-owned file with mode 0600:

```
NUCLEUS_SECRET=<long random string, same as the Worker's>
NUCLEUS_LLM_URL=https://integrate.api.nvidia.com/v1/chat/completions
NUCLEUS_LLM_MODELS=nvidia/nemotron-3-super-120b-a12b,z-ai/glm-5.3
NUCLEUS_LLM_KEY=<the owner's key>
```

`python3 hosted/nucleus_host.py` then serves on `127.0.0.1:8099`. Put nothing else of value
on that VM, and give it no credentials that matter.
